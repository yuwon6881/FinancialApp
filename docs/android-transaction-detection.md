# Android transaction detection

This feature is optional and local to a FinancialApp account on an Android installation. Enable Transaction detection in Settings → Plan & Preferences; after consent the app opens Android's access settings only when access is still missing, then asks for source apps. Manage detection (or Finish setup, while incomplete) shows the setup checklist. Source apps and Android notification access are required; the status stays Setup needed until both are ready. Review alerts and Unrestricted battery use are optional steps; the battery step opens App info, because OEM battery savers (Samsung, Xiaomi, Oppo/Vivo) otherwise stop the listener while the phone sleeps, and the battery-exemption dialog needs a Play-restricted permission. The Ledger shows the Detected transactions card only while detection is on or captures are waiting. Review alerts also require FinancialApp notification permission.

Only an alert Android delivers live, within five minutes of its posting, rings. When the listener reconnects (FinancialApp opened, reboot, or a rebind after Android stopped it), alerts still in the tray are captured as a catch-up replay: these, and stale re-posts, are added to the tray quietly, and a catch-up while FinancialApp is on screen adds no tray alert because the Detected transactions card already shows it. A live capture while FinancialApp is on screen is added quietly. All review alerts share one notification group with a silent summary, which is withdrawn once no review alert remains. Android may require **Allow restricted settings** in the app's Android App info menu for sideloaded APKs before notification access can be granted.

Play Protect installation blocking is separate from notification access setup. In some markets, Google blocks internet-sideloaded apps declaring notification-listener access. A different signing key or a release build does not guarantee removal of that block. Use an appropriate Google Play testing/distribution channel, or seek a classification appeal when warranted by the exact warning. Keep Play Protect enabled; this feature does not bypass it. See [Google's developer guidance](https://developers.google.com/android/play-protect/warning-dev-guidance).

App backgrounding protects the native task snapshot and schedules the app-access gate for return to FinancialApp. It does not mount the biometric prompt while Android Settings or another app is in front. Returning from settings still requires the existing app unlock.

Android grants access to the listener as a whole; the source selection is enforced by FinancialApp before notification content is inspected. Text is read from the expanded text, else an SMS/chat app's newest message (MessagingStyle), else inbox lines, else the collapsed line or ticker, so bank SMS alerts work when a messages app is a selected source. No-break and zero-width characters are normalised first.

Recognition describes payment wording, never particular apps, in English and Malay. An alert is captured when it names a payment with its outcome in either order ("Payment … successful", "Successful payment", "Pembayaran … berjaya"; nouns include DuitNow, DuitNow QR, JomPAY, FPX, IBG, GIRO, PayNow, auto-debit and short forms like txn/pmt/trf), uses a past-tense money verb beside a money figure (paid, spent, charged, debited, deducted, sent, transferred, dibayar, telah membayar …), or is a terse card alert with a card, a figure and a payee ("Card txn RM12.50 at 7-ELEVEN", "RM14.90 with Visa ••1234"). A bank-side top-up counts only when it names where the money went; a wallet's own "Reload successful" is money arriving. Excluded: codes (OTP/TAC/verification), approval prompts and requests, anything failed, declined, cancelled, "not successful" or "could not", anything unfinished (pending, processing, scheduled, submitted, on hold, "will be debited"), money arriving (received, credited, deposited, refunds, "paid to your account", money "from" someone with no payee), reminders and due notices, spending summaries, promotions, and limit or settings changes. The bare word "code" is not excluded, because QR payment confirmations use it.

The amount is the one distinct money figure, so a title and body repeating it still count once; figures labelled as a balance, limit, fee, cashback or reward are context, zero figures such as the "RM0" SMS prefix are ignored, and with several figures a single one labelled Amount/Total wins. Otherwise the amount stays blank. Codes (RM/MYR, SGD, USD, EUR, GBP, AUD, HKD, CNY, JPY, THB, IDR, PHP, INR and others), code-after-amount ("12.00 EUR") and unambiguous symbols (S$, US$, A$, HK$, £, €) are read; a bare "$" or "¥" leaves the currency and amount blank. The merchant comes from a labelled field ("Merchant:", "To:", "Penerima:"), else "at/to/kepada/di", else "for/untuk". It ends at a clause word, a following amount, a new line or sentence punctuation, keeping "of" and abbreviation periods inside names ("HOUSE OF NOODLES", "ACME SDN. BHD."); instruments ("your debit card", "Visa 1234"), times, masked numbers and dates are never taken as a merchant. Dates are read as ISO, day-first numeric with two- or four-digit years (`28/09/26`, the Malaysian/Singaporean convention, so US-style month-first numeric dates are misread), or with English or Malay month names (`28 Sep 2026`, `28-Sep-26`, `1 Ogos 2026`, `Sep 28, 2026`). Due, expiry and "next" dates are ignored, and two different dates or an impossible one stay absent. Transfer alerts open as ordinary outflow/purchase drafts. The rules are exercised by a corpus test of representative bank, card, wallet and SMS formats; they do not guarantee every app's wording. Alerts that carry no details ("You have a new notification"), cash withdrawals, and other languages are not captured.

Source selection is answered from an in-memory copy of the active owner's selected packages, refreshed on every store read and write, so unrelated notifications never decrypt the store. A capture is flagged as a possible duplicate when the same source repeats identical alert text within 10 minutes (including already-saved captures) or the same amount within 2 minutes. A possible duplicate never rings; it is added to the tray quietly. Only alerts still in the tray when the listener reconnects can be recovered; an alert swiped away while Android had detection stopped is lost, which is why the Unrestricted battery step matters.

The Android listener stores candidates using Android Keystore AES-GCM and an atomic file in the app's no-backup directory. No notification stream is uploaded. The local review notification contains generic copy and a candidate ID, not financial details. Capture pauses on sign-out and retains candidates for their originating account. The explicit local-data wipe removes captures. Up to 200 pending candidates are retained; completed notification identities are retained for 30 days with a bounded store.

Tapping a review notification waits for the existing native/session gates and sensitive-mode reveal, then opens the Ledger form. Category and description AI requests run only in authenticated review and offer choices, never automatic assignments. The reviewer chooses a ledger category and account before saving a captured transfer as an outflow; they can change its type to Transfer and then choose source and destination buckets and accounts. Foreign/unknown-currency amounts require explicit entry in the account currency. When the alert text carries no date, the posting date is the alert's arrival date in the financial time zone, and the form says so. A review opened while balances are hidden opens itself once they are revealed. Closing preserves review edits; a capture that no longer exists does not hold the form open. Dismissing an Android notification does not discard its candidate; use Ledger → Detected transactions to review or explicitly discard it.

Approved transactions use a native write-ahead approval and a stable transaction UUID. A fresh approval must pass the same rules as a Ledger draft (`getDraftTransactionIssues`) before it is stored. The outbox must persist before capture completion. Interrupted approvals resume after unlock using the original payload/UUID; each resumes independently, so one that cannot finish does not block other captures or a tapped review. A transaction the outbox already holds — synced, queued, or kept as a recoverable failure — completes its capture; retry or discard then happens in the outbox. The API's existing create-by-ID idempotency prevents duplicate transactions. The explicit local-data wipe withdraws only review notifications. The initial capture form does not attach receipts; documents can be added later using normal Ledger editing.

## Verification

- Frontend: `npm run lint`, `npm run check:design-system`, `npm run typecheck:strict`, `npm run deadcode`, `npm test -- --maxWorkers=4`, `npm run build`, `npm run test:visual`.
- Native: `npm run native:sync:android`, then `android/gradlew lintDebug testDebugUnitTest assembleDebug` with Java 21 and SDK 36.
- Browser native-bridge simulations verify the shipped review/settings UI, but do not establish handset notification delivery or provider coverage.
- Handset acceptance: upgrade the stable-signed APK; grant access; compare selected/unselected app alerts; test foreground/background/cold-start taps, unlock cancellation, sensitive mode, offline editing/saving, dismissal, duplicate alerts, catch-up after the listener was stopped (quiet, grouped, no burst on opening FinancialApp), battery Unrestricted vs optimized while locked, permission revocation, reboot, sign-out/account switching, and source formats from real banks/wallets.

The GitHub Android workflow bundles the native web app, syncs Capacitor, runs Android checks, and publishes the stable-signed device-test APK as an Actions artifact. Downloadable GitHub release assets must come from that workflow's exact commit rather than a locally signed debug build.
